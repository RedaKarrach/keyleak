keyleak

Did your AWS key just end up on GitHub?

Take a breath. keyleak reads your own AWS logs and tells you what the attacker did and what is still running. One command. It never touches the stolen key.

The first ten minutes

This is what a leak usually looks like. Press play.

Pick your situation

Different starts, same three steps.

The bill is the attacker's work showing up late. The spending may still be going on.

  1. Find the key. Look in the GitHub secret-scanning alert, your AWS notifications, or IAM → Users → Security credentials for a key you don't recognise using.
  2. Run keyleak investigate <KEY> then keyleak sweep. Terminate what you don't recognise. Delete every user and key it lists, not just the first one.
  3. Run keyleak report and send the generated message to AWS Support. They often refund first-time incidents if you show what happened and what you fixed.

GitHub's scanner found it, which means the bots probably did too. Assume it has been used.

  1. Copy the key ID (the AKIA… part) from the alert. You never need the secret.
  2. Run keyleak investigate <KEY>. If the verdict is suspicious, follow it with keyleak sweep and clean up what it shows.
  3. Run keyleak contain <KEY> --confirm to switch the key off, then remove it from the repo history too.

AWS saw the key in public and may have put a "quarantine" policy on the user. That limits the damage but does not undo what happened.

  1. The email names the key. Use that ID.
  2. Run keyleak investigate <KEY>. The quarantine blocks a few expensive actions, not all of them, so check.
  3. Clean up what keyleak sweep finds, switch the key off with contain, and reply to AWS with the report.

Good. You are early. Minutes matter here.

  1. Switch the key off right now: keyleak contain <KEY> --confirm, or do it in the IAM console. Make a new key for yourself afterwards.
  2. Then check whether anyone got there first: keyleak investigate <KEY>.
  3. Remove the key from the repo and its history. GitHub's docs on removing sensitive data cover it.

Four commands

Three of them only read. One makes a single change, and only when you say so.

read-only

investigate

Pulls every log line for the key, from every region, sorts the attacker's moves into categories, and follows every user or key they created.

read-only

sweep

Lists what is still running and still costing you: machines, functions, and any users or keys created after the leak.

one change

contain

Switches the leaked key off. Not deleted, just off. Refuses to run without --confirm. Touches nothing else.

read-only

report

One HTML file with the timeline, what is still running, what you did, and a ready-to-send message to AWS Support asking for a refund.

"Delete the leaked key" is where most advice stops. Try it.

Why it is safe to run while you are stressed

It never uses the leaked key

You run it as yourself, with your own login. The leaked key is just a search term. If you accidentally point it at the leaked key, it refuses to start.

Read-only by default

investigate, sweep and report change nothing. contain changes one thing, says exactly what it changed, and needs --confirm.

Nothing leaves your machine

It talks to AWS and writes two small files in your home folder so report can find the last run. No accounts, no telemetry.

Least privilege

A ready-made read-only policy with the handful of permissions it needs ships in the repo. Attach it to a user and run with that.

For developers

Python 3.11+, boto3, click, rich. MIT. Tests run with no AWS account.

How investigate works, in five lines
  1. Validates the key ID and refuses if your own credentials are that key.
  2. Resolves the owner via iam:GetAccessKeyLastUsed, then calls cloudtrail:LookupEvents for the key in every enabled region, with backoff on throttling and a note that event history only covers 90 days.
  3. Classifies each event: persistence (CreateUser, CreateAccessKey, CreateLoginProfile, AttachUserPolicy, PutUserPolicy, UpdateAssumeRolePolicy, CreateRole), cryptomining (RunInstances and friends, worse in a region you don't use), SES, Bedrock, and discovery from unfamiliar IPs.
  4. The pivot: every CreateUser, CreateAccessKey, CreateLoginProfile and AssumeRole in the history becomes a new identity to investigate, breadth-first, with a depth limit and a visited set. Keys IAM lists on an attacker-made user are followed too.
  5. Prints a verdict, the identities found and how, flags by category, attacker IPs and user agents, and the timeline. Saves JSON for report.
Permissions

Read-only commands: cloudtrail:LookupEvents, iam:Get*, iam:List*, ec2:Describe*, lambda:List*, sts:GetCallerIdentity. Shipped as docs/keyleak-readonly-policy.json. contain adds iam:UpdateAccessKey.

Tests and a safe live demo

The suite uses botocore's Stubber. The attacker scenario (leaked key → CreateUser → CreateAccessKey → RunInstances in an unused region) is a fixture, and the tests assert both that it is flagged and that keyleak pivots to the new key.

pip install -e ".[dev]"
python -m pytest

To see a real detection, docs/DEMO.md walks through playing the attacker with Stratus Red Team in a throwaway account.

What it can't do
  • CloudTrail event history is 90 days. Older activity is gone unless you had a trail in S3, which keyleak does not read.
  • It sweeps EC2, Lambda and IAM. Check the billing console for ECS, SageMaker, Lightsail, Bedrock and SES.
  • It is a first-response tool, not a forensic suite, and it does not clean up for you.
